## 1. Which integer the contract's own d_ff definition must return

The positive control is the direct presentation at m = 2:
generators S_3(x_1, x_2, x_R) (degree 4, top form x_1^2 x_2^2) and
f_V(x_k) = prod_{v < B}(x_k - v) (degree B, top forms x_1^B, x_2^B), in
F_p[x_1, x_2]. `measure_direct_system` reads `first_nonzero_fall`, i.e. the
first D with fall_dim(D) = full_rank(D) - top_rank(D) > 0 — the same definition
used on the Semaev arm.

fall_dim(D) > 0 requires a degree-D dependency among the **top forms** that does
not lift. The syzygy module of the monomial ideal (x_1^B, x_2^B, x_1^2 x_2^2) in
two variables is generated by the three lcm syzygies:

| pair | lcm | degree |
|---|---|---|
| (x_1^B, x_1^2x_2^2) | x_1^B x_2^2 | **B + 2** |
| (x_2^B, x_1^2x_2^2) | x_1^2 x_2^B | **B + 2** |
| (x_1^B, x_2^B) | x_1^B x_2^B | 2B |

so there is **no** top-form dependency below B + 2, and there are exactly **two**
at B + 2. Neither lifts (x_1^{B-2} S_3 - x_2^2 f_V(x_1) is a nonzero polynomial
of degree < B + 2), so

    d_ff = B + 2, with fall_dim(d_ff) = 2.

The frozen prediction B + 1 is the **semi-regular d_reg** of the Hilbert series
(1 - z^B)^2 (1 - z^4)/(1 - z)^2, whose coefficients are 1,2,3,4,4,...,4 then
2 at D = B, **0 at D = B + 1**, -2 at D = B + 2 (the run record's
`series_raw_coefficients` in `runs/RUN-PFDR-fd901a-posctrl-p4099/raw-result.json`
ends ..., 4, 2, 0, -2). d_reg = B + 1 is also the first degree at which the top
block reaches full column rank. IDEA-20260808-093497's "null d_reg = B + 1" is
therefore a **degree of regularity**, and the contract transcribed it into a
prediction for a **first fall**. Under the contract's own d_ff definition the
frozen integer 65 / 129 was **not satisfiable by any instance**.

## 4. The defect the plan did not name: the control has no dynamic range in p

d_ff = B + 2 is a function of **B alone**. Verified at fixed B = 8 across
p = 4099, 16411 and 2^64 - 59: d_ff = 10 at all three (§2, row B = 8). Since
B = round(p^{1/2}) is a deterministic function of p, the control's movement
66 -> 130 is entirely explained by the change of matrix shape, and a pipeline
that ignored p altogether — computing over Z, or modulo the wrong prime — would
produce exactly the same 66 / 130. **CTRL-POSITIVE-P-DEPENDENCE therefore does
not discharge falsification condition F2 ("the instrument is blind to p") for
the fixed-shape sweep it is supposed to gate.** Objection RT-O5.

The gap is closable and I closed it: running the **same fixed-shape (2,2,3)
construction through the producer's own meter** at p = 2 and p = 3 gives a
different profile from the 2^64 one (0 of 24 at p = 2; 1 of 24 dropped at p = 3),
matching my own code draw for draw (`out/proves_too_much.json`). The instrument
is demonstrably p-sensitive at fixed shape; the contract simply never asked it.
Note that Stage 0's small-prime table used the sympy/naive route
(`independent_macaulay_ranks`), **not** the meter, so the package as committed
contains no fixed-shape p-sensitivity check of the meter itself.
