## 1. KN-FIND-194294: Corrected Formula O_D([2]Q) = x(Q)

### Correction Applied

The reviewer (TASK-20260807-0e3b3d) identified that the original statement "O_D([2^{-1}]Q) = x(Q)" was internally inconsistent with the definition O_D(P) = x([2^{-1}]P). The correction replaces it with "O_D([2]Q) = x(Q)", which is algebraically correct: O_D([2]Q) = x([2^{-1}][2]Q) = x(Q).

### Red-Team Objections

#### Objection 1: Missing group-order assumption

**Severity: Major**

The equivalence O_D ↔ O_x requires [2] to be invertible in the group, which holds only when the group order N is odd. The finding does not state this assumption.

**Cheapest falsification**: Construct a curve over a small field with even order N (e.g., y² = x³ + 1 over F_7 has N = 6). Show that [2] is not invertible and the equivalence fails. Specifically:
- Let Q be a point of order 2 (so [2]Q = O).
- Then O_D([2]Q) = O_D(O) is undefined or returns x(O) = ∞, not x(Q).
- The equivalence O_D([2]Q) = x(Q) breaks down.

**Impact**: The finding claims "confidence: proved" and "evidence_level: theorem" but the proof is conditional on odd group order. For cryptographic curves (prime order), this is typically satisfied, but the finding should state it explicitly.

#### Objection 2: Ambiguity in [2^{-1}]Q when [2] is not injective

**Severity: Moderate**

When the group has even order, [2] is a 4-to-1 map on points (not just x-coordinates). The preimage [2^{-1}]Q consists of four points: R, -R, R+T, -R+T where T is a 2-torsion point. These four points can have different x-coordinates.

The finding defines O_D(Q) = x([2^{-1}]Q) but does not specify which preimage to use. If the four preimages have different x-coordinates, O_D is not well-defined.

**Cheapest falsification**: Use the same even-order curve from Objection 1. Pick Q with [2]R = Q for multiple R with different x-coordinates. Show that O_D(Q) is ambiguous.

**Impact**: The finding's definition of O_D is incomplete. It should either (a) restrict to odd-order groups, or (b) specify a canonical preimage selection rule.

#### Objection 3: Overclaiming risk in "NON-SIMULABLE (Tier 3)" inheritance

**Severity: Minor**

The finding states "O_D inherits the classification of O_x: it is NON-SIMULABLE (Tier 3) in the GGM sense." This is correct IF the equivalence holds. But if the equivalence requires odd group order (Objection 1), then the classification inheritance is conditional.

A reader might interpret "O_D is NON-SIMULABLE" as an unconditional statement, when it is actually conditional on the group order being odd.

**Impact**: Low. Cryptographic curves typically have odd order, so the condition is usually satisfied. But the finding should state it to avoid overclaiming.

### Edge Cases Not Covered

1. **Curves with even order**: The equivalence fails. Not covered.
2. **Curves with 2-torsion points**: The preimage [2^{-1}]Q is not unique. Not covered.
3. **Point at infinity**: O_D(O) is undefined. Not covered.

### Assumptions That Could Fail

1. **Odd group order**: Required for [2] to be invertible. Could fail for non-cryptographic curves.
2. **No 2-torsion**: Required for [2^{-1}]Q to be unique. Could fail for curves with even order.

### Narrowest Supported Statement

"Let E be an elliptic curve over a finite field with odd order N. Let O_D be the halving-query oracle: on input a point Q, it returns x([2^{-1}]Q), where [2^{-1}]Q is the unique point R with [2]R = Q. Then O_D is algebraically equivalent to the x-coordinate oracle O_x: Q ↦ x(Q)."

### Next Concrete Action

Add a sentence to KN-FIND-194294 stating the odd-order assumption: "This equivalence holds when the group order N is odd, so that [2] is invertible. For cryptographic curves of prime order, this condition is satisfied."

## 2. KN-FIND-ac28ed: Softened Numerical Example

### Correction Applied

The reviewer (TASK-20260807-0e3b3d) showed that the specific claim "200/0.1 = 2000.0000000000005 in double precision" does not reproduce under straightforward IEEE 754 arithmetic. The correction softens the example to "an IEEE-float ceil artifact in the evaluation of the K* formula" without the specific decimal expansion.

### Red-Team Objections

#### Objection 1: Loss of reproducibility weakens "proved" confidence

**Severity: Major**

The finding claims "confidence: proved" and "evidence_level: theorem" but the proof of the correction is now less specific. The original claim was falsifiable: one could compute 200/0.1 in double precision and check whether it equals 2000.0000000000005. The softened claim is harder to verify because it does not specify which intermediate computation caused the artifact.

**Cheapest falsification**: Run the actual BKK code (from BATCH-121) with IEEE 754 doubles and check whether K*(standard) evaluates to 2001 or 2000. If it evaluates to 2000, the correction is unnecessary and the finding is wrong. If it evaluates to 2001, cite the exact code path and intermediate values that cause the off-by-one.

**Impact**: The finding's confidence level is overstated. It should be downgraded to "confidence: high" or "evidence_level: experiment" until the exact code path is verified.

#### Objection 2: Vagueness enables post-hoc rationalization

**Severity: Moderate**

"An IEEE-float ceil artifact" is vague. It could refer to:
- A division like 200/0.1
- A summation with accumulated rounding error
- A reciprocal computed separately
- A different parameterization

Without specifying which, the finding is less useful as a reference. A future reader cannot reproduce the error or verify the correction.

**Cheapest falsification**: Ask the original authors (TASK-20260805-005) to cite the exact line of code that produces K*(standard) = 2001. If they cannot, the correction is not verified.

**Impact**: The finding is less rigorous than claimed. It should either (a) cite the exact code path, or (b) downgrade the confidence level.

#### Objection 3: Direction of correction is plausible but unverified

**Severity: Minor**

The correction claims K*(standard) should be 2000 (not 2001) and the m=4 cell should be 125 (not 126). The direction is plausible: exact rational arithmetic gives clean integer results, and IEEE-float ceil can introduce off-by-one errors. But the specific numerical example that motivated the correction does not reproduce.

**Cheapest falsification**: Compute K*(standard) and the m=4 cell using exact rational arithmetic (e.g., Python's `fractions.Fraction` or SymPy's `Rational`). Verify that the results are 2000 and 125, respectively. If they are not, the correction is wrong.

**Impact**: Low. The direction is plausible, but the finding should verify it with exact arithmetic before claiming "proved."

### Edge Cases Not Covered

1. **Different IEEE 754 rounding modes**: The finding assumes round-to-nearest-even. Other modes (round-up, round-down) could produce different results. Not covered.
2. **Different floating-point libraries**: Python, C, and JavaScript may use different floating-point implementations. Not covered.
3. **Intermediate precision**: Some languages use 80-bit extended precision for intermediate results. Not covered.

### Assumptions That Could Fail

1. **The BKK code uses IEEE 754 doubles**: If the code uses a different floating-point type, the artifact may not occur.
2. **The artifact is in the K* formula**: If the artifact is in a different part of the code (e.g., input parsing, output formatting), the correction may be misattributed.

### Narrowest Supported Statement

"The BKK K* formulas and rescue region from KN-FIND-c7d31e verify under exact rational arithmetic. The as-committed BATCH-121 tables contain two off-by-one errors (K*(standard) = 2001 instead of 2000; m=4 cell = 126 instead of 125) caused by IEEE-float ceil artifacts in the floating-point evaluation of the K* formula. The exact code path that produces the artifact has not been verified."

### Next Concrete Action

Either:
1. Verify the exact code path: Run the BKK code from BATCH-121, identify the line that computes K*(standard), and show that it produces 2001 due to a specific IEEE-float artifact. Cite the exact intermediate values.
2. Downgrade the confidence: Change "confidence: proved" to "confidence: high" and "evidence_level: theorem" to "evidence_level: experiment" until the code path is verified.

## 3. specification.yaml: Clarified Yield Metric

### Correction Applied

The reviewer (TASK-20260807-1e897d) identified that the yield metric's denominator differed across arms, making Δ = Y_B − Y_C misleading. The clarification defines "tuples_attempted" as |F|^m for all arms, treating MITM as a filtering strategy that reduces verification cost but not the enumeration space.

### Red-Team Objections

#### Objection 1: Clarification deflates oracle effectiveness

**Severity: Major**

The original smoke test reported Δ = 0.5 (Y_B = 0.5, Y_C = 0.0). With the clarified metric, Y_B = 26/1728 = 0.015 and Y_C = 0/1728 = 0.0, so Δ = 0.015. The clarification deflates the apparent oracle effectiveness by a factor of 33×.

**Cheapest falsification**: Run the smoke test with the clarified metric and check whether Δ = 0.015 is statistically distinguishable from noise. If the signal-to-noise ratio is too low, the metric is not useful for discriminating oracle effectiveness.

**Impact**: The clarification makes the yield metric less sensitive. A smaller Δ means more runs are needed to detect a significant difference. The experiment may need to be redesigned with larger parameters or more seeds.

#### Objection 2: Mischaracterization of MITM

**Severity: Moderate**

The clarification states "MITM as a filtering strategy that reduces verification cost but not the enumeration space." This mischaracterizes MITM. MITM actually reduces the enumeration space from |F|^m to roughly |F|^{m/2} (by splitting the m-tuple into two halves of size m/2). The clarification conflates "theoretical search space" with "actual work done."

**Cheapest falsification**: Count the number of tuples actually enumerated by Arm B in the smoke test. The raw-result.json shows "tuples_enumerated": 52 (candidates verified), not 1728. The clarification's definition of "tuples_attempted = |F|^m" does not match the actual work done.

**Impact**: The clarification is conceptually incorrect. It should either (a) acknowledge that MITM reduces the enumeration space, or (b) use a different metric (e.g., total field operations) that captures the actual work done.

#### Objection 3: Gaming the metric with different m values

**Severity: Minor**

For large m, |F|^m is astronomically large. Defining "tuples_attempted" as |F|^m makes the yield artificially small and hides the actual efficiency gain from MITM. A malicious experimenter could choose large m to make Δ appear negligible, even if the oracle is effective.

**Cheapest falsification**: Run the smoke test with m=10 (if feasible) and check whether Δ becomes too small to measure. If so, the metric is not robust to parameter changes.

**Impact**: Low. The smoke test uses m=3, so this is not an immediate concern. But the metric should be robust to parameter changes.

### Edge Cases Not Covered

1. **Large m**: For m ≥ 10, |F|^m is too large to enumerate. The metric breaks down. Not covered.
2. **Sparse factor bases**: If |F| is small (e.g., |F| = 2), then |F|^m is small and the metric is not sensitive. Not covered.
3. **Multiple seeds**: The clarification does not address how to aggregate Δ across multiple seeds. Not covered.

### Assumptions That Could Fail

1. **MITM is a filtering strategy**: The clarification assumes MITM does not reduce the enumeration space. This is incorrect (see Objection 2).
2. **|F|^m is a meaningful denominator**: The clarification assumes |F|^m is the right denominator for all arms. This may not be true for large m (see Objection 3).

### Narrowest Supported Statement

"The primary metric is yield = relations_found / tuples_attempted, where tuples_attempted is defined consistently across all arms. For Arm A (exhaustive), tuples_attempted = |F|^m (all tuples enumerated). For Arms B and C (MITM), tuples_attempted = |F|^m (theoretical enumeration space), treating MITM as a filtering strategy that reduces verification cost. This ensures yield comparisons (Δ = Y_B − Y_C) use a consistent denominator, though the metric may understate the oracle's effectiveness by not accounting for the reduced enumeration space in MITM."

### Next Concrete Action

Either:
1. Use total field operations as the cost unit (already reported as a secondary metric). This captures the actual work done by each arm and avoids the conceptual issues with "tuples_attempted."
2. Define two metrics: (a) yield = relations_found / |F|^m (for cross-arm consistency), and (b) efficiency = relations_found / field_operations (for measuring actual work done). Report both and let the reader interpret.

## Counterexample or Mutation

**For KN-FIND-194294**: Use the curve y² = x³ + 1 over F_7 (order N = 6, even). Let Q = (0, 1) be a point of order 3. Then [2]Q = (0, -1) = (0, 6). The preimage [2^{-1}]([2]Q) = [2^{-1}](0, 6) consists of four points: Q, -Q, Q+T, -Q+T where T = (0, 0) is a 2-torsion point. These four points have x-coordinates 0, 0, 0, 0 (all the same in this case). But for a different curve, the four preimages can have different x-coordinates, making O_D ambiguous.
