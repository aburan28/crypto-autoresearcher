## 1. KN-FIND-194294 — Halving-query oracle equivalence

### Review feedback addressed

TASK-20260807-0e3b3d identified a formula-direction error: the Statement
section originally read `O_D([2^{-1}]Q) = x(Q)`, which is inconsistent with
the definition `O_D(Q) = x([2^{-1}]Q)`. The reviewer required correction to
`O_D([2]Q) = x(Q)`.

### Current state (line 19)

> Specifically, a single halving-query O_D([2]Q) = x(Q) recovers the target
> x-coordinate in one call

### Independent mathematical verification

**Direction 1 (O_D → O_x):** By definition, O_D(P) = x([2^{-1}]P) for any
input point P. Substituting P = [2]Q:

    O_D([2]Q) = x([2^{-1}] · [2]Q) = x([2^{-1} · 2]Q) = x([1]Q) = x(Q).

This is correct. The corrected formula recovers x(Q) in one oracle call. ✓

**Direction 2 (O_x → O_D):** Given x(Q), compute O_D(Q) = x([2^{-1}]Q).
Let R = [2^{-1}]Q, so [2]R = Q. The duplication formula gives x([2]R) as a
degree-4 rational function of x(R):

    x([2]R) = (x(R)^4 − 2A·x(R)^2 − 8B·x(R) + A^2) / (4·(x(R)^3 + A·x(R) + B))

Setting x([2]R) = x(Q) yields a degree-4 polynomial equation in x(R), solvable
in O(1) field operations. The solution x(R) = x([2^{-1}]Q) = O_D(Q). ✓

**Equivalence conclusion:** O_D and O_x are algebraically equivalent, each
recoverable from the other in O(1) work. The NON-SIMULABLE (Tier 3)
classification inheritance is sound. ✓

### Verdict

**PASS.** The correction is mathematically sound. The original intent
(equivalence of O_D and O_x) is preserved and now stated with a correct
formula. No residual errors detected.

## 2. KN-FIND-ac28ed — Exact-arithmetic corrections to BKK K* table

### Review feedback addressed

TASK-20260807-0e3b3d identified that the specific numerical example
"200/0.1 = 2000.0000000000005 in double precision" does not reproduce under
standard IEEE 754 double-precision arithmetic. The reviewer offered two
remedies: (a) verify against the actual BKK code path and cite it, or
(b) soften the example to avoid the unreproducible decimal expansion.

### Independent arithmetic verification

I independently verified the IEEE 754 double-precision computation:

    >>> 200.0 / 0.1
    2000.0
    >>> math.ceil(200.0 / 0.1)
    2000

The double nearest 0.1 is 0.10000000000000000555111512... (slightly above
0.1). The quotient 200.0 / 0.1_double = 1999.999999999999889..., which rounds
to exactly 2000.0 in double precision (the error ~1.11e-13 is less than half
an ULP at 2000). Therefore ceil(200.0 / 0.1) = 2000, not 2001.

**The reviewer's analysis is confirmed:** the specific numerical example as
originally stated does not reproduce.

### Current state of the finding

The finding now reads (line 23):

> | K*(standard) | 2001 | **2000** | IEEE-float ceil artifact in the evaluation of the K* formula; exact rational is 2000 |

And (line 24):

> | m=4 cell | 126 | **125** | Same IEEE-float ceil artifact |

The specific decimal expansion "2000.0000000000005" has been removed. The
cause is now stated as "IEEE-float ceil artifact in the evaluation of the K*
formula" without claiming a specific unreproducible intermediate value. This
corresponds to the reviewer's option (b).

### Assessment of softened presentation

The softened statement is:
- **Mathematically honest:** It does not assert a specific floating-point
  intermediate that fails to reproduce. ✓
- **Sufficiently informative:** It correctly identifies the mechanism (IEEE-float
  ceil artifact) and the direction of correction (2001→2000, 126→125). ✓
- **Consistent with the underlying claim:** The K* formulas are exact; only the
  floating-point evaluation introduced off-by-one errors. The K*(BKK)=96
  confirmation is consistent. ✓
- **Preserves original intent:** The correction still communicates that the
  as-committed tables contained IEEE-float artifacts and that exact rational
  arithmetic gives clean integer results. ✓

### Verdict

**PASS.** The softened numerical presentation adequately conveys the correction
without asserting an unreproducible specific decimal expansion. The underlying
correction claim (K*(standard)=2000, m=4 cell=125, K*(BKK)=96) remains sound.
The original intent is preserved.

**Residual limitation noted:** The finding does not cite the exact code path
that produced the off-by-one errors. This is acceptable for a finding at
`evidence_level: theorem` (the correction is derived from the formulas, not

## 3. specification.yaml — Yield metric clarification

### Review feedback addressed

TASK-20260807-1e897d (Finding F1) identified that the yield metric's
denominator differed across arms in the smoke test implementation:
- Arm A: |F|^3 = 1728 (all triples enumerated)
- Arm B: 52 (candidates verified after hash-table filter)
- Arm C: 20 (candidates verified after hash-table filter)

This made Δ = Y_B − Y_C = 0.5 misleading, since the denominators differed by
a factor of ~33×. The reviewer recommended clarifying the yield metric
definition before running the full cell grid.

### Current state (lines 55–62)

The specification now defines:

> yield: relations_found / tuples_attempted, where tuples_attempted is defined
> consistently across all arms as |F|^m (the full enumeration space). For Arm
> A (exhaustive), this equals the number of triples enumerated. For Arms B and
> C (MITM), this is the theoretical enumeration space |F|^m, treating MITM as
> a filtering strategy that reduces verification cost but not the enumeration
> space. This ensures yield comparisons (Δ = Y_B − Y_C) use a consistent
> denominator.

### Assessment of the clarified definition

**Unambiguousness:** The definition is now explicit and unambiguous:
- The denominator is |F|^m for all arms. ✓
- The rationale is stated: MITM is a filtering strategy, not a reduction in
  the enumeration space. ✓
- The purpose is stated: to ensure Δ comparisons use a consistent denominator. ✓

**Implementability:** The definition is implementable:
- |F| is determined by the factor base rule (B = floor(p^b) x-coordinates,
  each with 2 points, so |F| = 2B). ✓
- m is an input parameter. ✓
- |F|^m is computable before the run. ✓
- All arms use the same denominator, so the implementation must report
  relations_found / |F|^m for each arm. ✓

**Consistency with the smoke test results:** Under the clarified definition,
the smoke test results would be:
- Y_A = 26 / 1728 = 0.01505 (unchanged, since |F|^3 = 1728)
- Y_B = 26 / 1728 = 0.01505 (denominator corrected from 52 to 1728)
- Y_C = 0 / 1728 = 0.0 (denominator corrected from 20 to 1728)
- Δ = Y_B − Y_C = 0.01505

This is a more honest comparison: the x-oracle does not increase the number
of relations found (Arm B finds the same 26 relations as Arm A), it only
reduces the verification cost. The clarified metric correctly reflects this. ✓

**Preservation of original intent:** The original intent was to compare the
effectiveness of the x-oracle vs. a random oracle in finding relations. The
clarified metric shifts the comparison from "how many relations does each arm
find per candidate verified" (which favored MITM due to denominator choice) to
"how many relations does each arm find per unit of enumeration space" (which
correctly shows that both arms find the same relations, but MITM verifies
fewer candidates). This is a more meaningful comparison. ✓

### Verdict

**PASS.** The yield metric definition is now unambiguous, implementable, and
consistent across arms. The clarification correctly addresses Finding F1 from
TASK-20260807-1e897d. The original intent is preserved and the metric now
correctly reflects the oracle's value (reducing verification cost, not
increasing relations found).
