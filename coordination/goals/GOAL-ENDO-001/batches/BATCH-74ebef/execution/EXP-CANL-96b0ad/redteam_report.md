## 1. Hunt 1 — the f_E gap is very likely the real story, and it is not fixed by a bigger ladder

**The argument, in full.**

1. `harness/isogeny_class.py:285-286`: `frobenius_discriminant(p, t) = t*t - 4*p`.
   This is `disc(Z[π])` — the discriminant of the order generated by
   Frobenius *alone*. `fundamental_discriminant` then factors it as
   `D0 * f²`. Every `f_E` reported anywhere in this run — the execution
   report's table (`f_E ∈ {8, 48, 14, 2}`), `run_canl.py:611,674,778` — comes
   from this single code path, applied per-twist in the
   "no c2-congruence-ladder prime realizes `f_E=1`" exhaustive check
   (`execution_report.md` §4, `run_canl.py:870-880`).

2. `Z[π] ⊆ End_{F_p}(E)` always, but the containment can be strict. This is
   standard (Waterhouse; the isogeny-volcano literature, e.g. Kohel,
   Fouquet–Morain, Sutherland): the *true* `F_p`-rational endomorphism ring
   can properly contain the order generated by Frobenius alone whenever
   another `F_p`-rational endomorphism exists that isn't already in `Z[π]`.

3. For `j=0`, `p ≡ 1 (mod 3)`, that "another endomorphism" is always
   available and always rational: `σ: (x,y) → (μx,y)`, `μ³=1`, `μ ∈ F_p`.
   Check it directly on `y² = x³+A`: `(μx)³+A = μ³x³+A = x³+A`, identically
   in `A`. So `σ` is an automorphism of **every** sextic twist, for **every**
   `A`, requiring no field extension — it is `F_p`-rational by construction,
   on every one of the 6 twists this run's own exhaustive check iterates
   over.

4. `σ`, viewed inside `End(E) ⊗ Q ≅ K = Q(√-3)`, is (up to sign/orientation)
   literally `ζ₃`. This is exactly what `H-CANL-e59a06`'s own `assumptions`
   block already states as a fact "verified constructively, not assumed,"
   and it is exactly what `G3`'s tautology gate empirically confirms: the
   group-law identity `P + σP + σ²P = O` holding at **every** one of 4000
   sampled points, across all 4 primes, with 12 independently re-verified
   certificates, is precisely the statement that `σ` satisfies the minimal
   polynomial of `ζ₃` acting on the curve's group — i.e. that `σ` really is
   `ζ₃` in `End_{F_p}(E)`, not merely an abstract order-3 automorphism of the
   curve as a variety.

5. `Z[ζ₃]` *is* the maximal order `O_K` of `Q(√-3)` (a textbook fact: the
   ring of integers of `Q(√-3)` is generated over `Z` by `ζ₃` alone). So any
   subring of `K` containing `ζ₃` automatically contains `Z[ζ₃] = O_K`, and
   since no order in `K` can properly contain the maximal order,
   `End_{F_p}(E) ⊇ Z[ζ₃] = O_K` forces `End_{F_p}(E) = O_K` exactly.
   `f_E := [O_K : End_{F_p}(E)]^{1/2}`-style conductor of the *true*
   endomorphism ring is therefore **1, unconditionally, on every twist, at
   every prime with `p ≡ 1 (mod 3)`** — regardless of what `Z[π]`'s own
   conductor happens to be.

If this is right, "none of the 6 twists is maximal" (`execution_report.md`
§4, `run_canl.py:870-880`'s comment) is a true statement about `Z[π]` and a
false statement about `End_{F_p}(E)` — the two rings are being conflated
under one name, `f_E`, throughout this run's code and report. `Z[π]` having
conductor `> 1` on its own is unremarkable (it just means Frobenius alone
doesn't happen to generate the full ring at these small primes); it says
nothing about the *true* endomorphism ring once the always-present
automorphism is accounted for.

## 2. Hunt 2 — the 15% shell-count tolerance and the C0=1 threshold tie are genuine defects in how F6/F10 are posed, not merely a magnitude quibble

**Where "15%" comes from.** It is not derived anywhere in this record chain.
`IDEA-20260807-11b93d.yaml:358-366` states it directly as a `minimum_effect`
field alongside the shell-count prediction
`2πC₀²/√|D_E| + O(C₀|D_E|^{-1/4}+1)`, with no accompanying computation of the
`O(...)` term's actual implied constant. `H-CANL-e59a06` and
`EXP-CANL-96b0ad` carry the number forward unchanged (`P5`, `F6`). It reads
as a plausible round number chosen for legibility, not a bound derived from
the formula's own stated error term.

**Is it well-calibrated anyway?** Partially, and that partial fit is itself
the problem. At `D_E=-67, C0=5`: predicted `19.19`, observed `23`, absolute
discrepancy `3.81`. The formula's own disclosed correction term at these
values is `O(C0·|D_E|^{-1/4}+1) ≈ O(5·67^{-0.25}+1) ≈ O(2.7)` — the same
order of magnitude as the observed discrepancy. So the *absolute* error is
roughly where the formula's own big-O notice says it should be; the
*relative* error (19.9%) is large only because the **leading term itself is
small** at this `(C0, |D_E|)` pair (predicted count `≈19`). This is exactly
what the formula's asymptotic form predicts should happen at small counts —
a fixed relative-error tolerance and an asymptotic formula whose absolute
error is roughly constant-ish while its leading term shrinks are
structurally mismatched: relative error is *guaranteed* to spike precisely
in the corner the two failing cells sit in (largest `|D_E|` relative to
`C0`, i.e. smallest predicted shell). A percentage check cannot be
well-calibrated against an additive `O(...)` term without either (a)
restricting the claim's domain to where the leading term dominates
(`C0²/√|D_E|` above some threshold), or (b) stating the tolerance as an
absolute bound (`|observed − predicted| = O(C0)`) instead of a fixed
percentage.

**Does this call F6/F10 into question independent of the dual-tuple bug?**
Yes, and this is a distinct objection from "the tolerance number might be a
few points off." As currently posed, F6/F10 risk firing on exactly the
region the formula's own notation says not to trust as a percentage — which
means a future run could reach `C2_INSTRUMENT_INVALID` (or, in the other
direction, a false `C2_SUPPORTED` at a cell where the formula's error term
genuinely dominates but happens to land under 15%) for reasons that are
about the *check's own shape*, not about whether CM changes the escape-shell
count. The `C0=1` threshold tie is the same failure mode in a sharper form:
at `C0=1` the nonunit shell has 1 element on both sides of the boundary by
construction (there simply isn't room for the count to differ at that
resolution), so a tie-based sensitivity gate is guaranteed to be degenerate
at `C0=1` regardless of any real CM effect — this is a corner case the grid
itself chose to include (`C0_grid_full_enumeration: [1,2,3,5,8]`) without a
floor excluding it from a hard gate.

**This is genuinely separate from Hunt 1.** Stages A and E (where these two
findings live) enumerate shells directly against `class_number_one_
discriminants_frozen`'s abstract `D0` values, not curve-realized `D_E` —
so this issue is not resolved by fixing Hunt 1, and Hunt 1 is not resolved
by fixing this. CORR-20260810-308774's own scoping (leaving these "left open
pending independent review," not folding them into the dual-tuple fix) is
the right call; I am extending, not correcting, that scoping — and adding a
name for *why* they are separate: they live in different stages of the
pipeline, on different discriminant objects.

**Cheapest discriminating control.** Restate F6 as an absolute-error bound
(`|observed − predicted| ≤ c·(C0/|D_E|^{1/4} + 1)` for a stated, derived `c`
— even `c=2` computed once against the passing cells would be a real
derivation rather than a round percentage) or restrict its claimed domain to
`C0²/√|D_E| ≥` some stated floor, and exclude `C0=1` from the threshold-tie
hard gate by construction (report it as a degenerate-cell tail check
instead, which the contract's own `tail_checks` block already has a slot
for). Both are amendment-text changes, not new compute.

## 3. Hunt 3 — the one-run-for-the-grid design (D1) is fine for this run's outcome and structurally incompatible with the contract's own evidence-strength rule for a future one

`evidence_strength_calibration_frozen` requires "both C1 and C2 to reach a
`*_SUPPORTED` or clean-refuted state ... at all 3 seeds and on at least 4 of
5 main-ladder primes" for `replicated` strength, and explicitly says a
partial-agreement run caps at `preliminary` "and the dissenting prime/seed
must be named." That is a **per-prime** predicate. `run_canl.py`'s D1 design
computes exactly **one** aggregate terminal state per regime across the
whole grid (`decision-rule-evaluation.json`'s `global_state`/`c1_state`/
`c2_state`, each a single value, not a per-prime vector).

**Why it didn't matter here.** The dual-tuple bug's root cause
(CORR-20260810-308774) is in the auxiliary-weight construction itself, which
is prime-independent — it poisons every cell uniformly, so aggregating
across primes lost no information this time; the underlying per-cell numbers
are still all individually present in `c1-measurements.json`/
`c2-measurements.json` and could be disaggregated by hand.

**Why it will matter the moment a real verdict is in play.** Suppose a v2
run reaches, say, `C1_SUPPORTED` at 4 of 5 primes and a genuine
`C1_SLOPE_ANOMALY` at the fifth (a real, prime-specific numerical issue, not
a uniform code defect). The current `frozen_decision_rule` evaluates C1's
waterfall as a *single* pass through four mutually exclusive states — it has
no way to represent "4/5 primes reached `C1_SUPPORTED`, one dissented" as
its own terminal outcome; it would have to either (a) report the aggregate
as `C1_SUPPORTED` (silently discarding the dissent and implicitly claiming
5/5 agreement, i.e. `replicated`-strength language the contract's own text
does not license), or (b) report the whole run as failing at the first state
that catches the anomaly (`C1_SLOPE_ANOMALY` or `C1_INSTRUMENT_INVALID`),
discarding four genuinely clean primes. Either failure mode is exactly the
kind of contract-vs-design mismatch CORR-20260810-308774 already caught once
for the dual-tuple check — the fix belongs in the same amendment, not
deferred to "whichever run first surfaces it." The `evidence_strength_
calibration_frozen` text cannot currently be honored by any run this driver
produces, because the driver was never built to report a per-prime
pass/fail vector, only a single aggregate.

**Required control for v2.** Restructure `frozen_decision_rule` to evaluate
per `(regime, prime)` and roll up per the already-frozen `4/5` rule, or —
if D1's single-run auditability is worth keeping — at minimum add a
per-prime pass/fail table to the required artifacts and make the aggregate
terminal state a documented function of that table (e.g. "majority state,
with the minority prime named"), so `replicated` vs `preliminary` strength
is a *computed* property of the run record rather than something a
Coordinator has to reconstruct by hand from `c1-measurements.json`.

## 5. Hunt 5 — is there a cheaper path than a full v2 amendment?

**Given Hunt 1, resequence rather than parallelize CORR-20260810-308774's
two required-action items.** The correction's item 2 asks whether the
`f_E=1` gap needs "an extended or different C2-congruence-ladder rule" and
leaves that open pending review. If Hunt 1's argument survives its required
control (§1), the answer is very likely **no new ladder rule is needed at
all** — the existing four primes already realize the maximal order; only the
code path computing `f_E`/`D_E` for Stage D needs to use the ring the
tautology gate already constructively confirms, rather than `Z[π]`'s own
conductor. That is a cheaper, more targeted fix than redesigning
`c2_congruence_ladder_rule_frozen`, and — importantly — it should run
**first**, because it may change which cells are near Hunt 2's small-count
corner case (the maximal order's own shell at `D_E=-3` is a *different*
sequence of counts than the `f=8,48,14,2` suborders currently reported, so
re-deriving Hunt 2's tolerance calibration against the currently-reported
discriminants could be partly wasted effort if those discriminants are the
wrong ones for Stage D specifically).

**Dropping the dual-tuple check entirely, relying only on the 1%
certificate spot-check — not recommended, and not actually cheaper in the
way it looks.** The two checks test different things: the certificate
spot-check (`certificate_semantics`) re-derives whether a *sampled* residue,
once enumerated, was correctly reduced by a second reducer function — it
says nothing about whether the *enumeration itself* (the set of tuples
considered, the box bounds, the collision bookkeeping) is complete and
correct. A systematically wrong enumeration (an off-by-one in a box bound,
say) could still pass every spot-check while returning a wrong total count.
The dual-tuple check, whatever its current construction defect, exists to
catch exactly that class of bug by an independent path. Dropping it outright
trades a real (if currently mis-specified) category of defect detection for
none — a genuine rigor cost, not a redundant belt-and-suspenders removal.
CORR-20260810-308774's own proposed fix (weights satisfying the stated
Sidon/mixed-radix separation condition) is already fully derived and
specified in the correction record itself; implementing *that* is cheaper
than either redesigning the check's purpose or dropping it.

**Net recommendation.** A v2 amendment is still needed, but it is smaller
than "redo everything CORR flagged simultaneously": (1) first, run the
cheap f_E/maximal-order recomputation (§1) as a diagnostic against the
existing run's artifacts — no new dispatch; (2) fix the auxiliary-tuple
construction using CORR's own already-derived separation condition; (3)
restate F6 as an absolute-error bound and exclude `C0=1` from the
threshold-tie hard gate (§2); (4) add the per-prime pass/fail table needed
to honor `evidence_strength_calibration_frozen` (§3) before, not after, the
next dispatch produces a verdict that needs it. None of (2)-(4) is blocked
on (1), but (1) should be done first because its outcome plausibly changes
the discriminant set (2)-(3) need to be calibrated against.
