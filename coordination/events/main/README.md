# Merge events for `main`

One **write-once** YAML record per merge, named by the merge commit's short sha.
Generated by `tools/merge_digest.py`, published by
`.github/workflows/main-events.yml`.

## Why a feed and not a notification

**There is no way to push an event to "all runners."** Agent sessions are
ephemeral, and when a merge lands most of the sessions that will care about it
do not exist yet. The available MCP subscription (`subscribe_pr_activity`) is
per-pull-request, single-consumer, and bound to one live session — it cannot fan
out to N runners and cannot reach a session created tomorrow.

So the event is written where any future session can find it, instead of pushed
at sessions that are not there.

## What it adds over `git log`

For "which commits landed": **nothing** — use git. What this adds is the
*semantic* delta a resuming agent actually needs:

- which `GOAL-*` records changed **status** or **next_action**, with old → new;
- which ledger and knowledge records are new, by type;
- whether the **shared contract** moved (`AGENTS.md`, `CLAUDE.md`, `docs/`,
  `tools/`, `.github/`, `templates/`, `orchestration/`) — the files that bind
  every campaign at once.

An agent on a 40-behind branch answers "did anything change under my goal, or in
the rules I am bound by?" from one record rather than by diffing 40 commits.

## Reading it

```sh
# everything since your branch last shared history with main
python3 tools/merge_digest.py --since $(git merge-base HEAD origin/main) --until origin/main

# per-branch, for every open branch at once
python3 tools/sync_open_branches.py --digest
```

## Rules

- **Write-once.** One file per merge sha, so concurrent merges never touch the
  same bytes. Never edit or delete a record; a wrong digest is superseded by
  regenerating under a new name, exactly like any other immutable record.
- **Not authoritative.** The ledger is. This is a convenience index over it, and
  a disagreement means the digest is stale or buggy — never that the ledger is
  wrong.
- Records here are excluded from the workflow's own trigger, so publishing one
  does not retrigger the workflow.
