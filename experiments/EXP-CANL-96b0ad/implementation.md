# Implementation note — EXP-CANL-96b0ad

Every deviation from the frozen contract, in full, per AGENTS.md rule 9 and
the handoff's own instruction. Nothing below is absorbed silently; each item
is also documented at the point in `harness/run_canl.py` /
`harness/exp_canl.py` / `harness/canonical_height.py` where it matters.

## D1 — one run record for the whole sweep, not one per (arm, prime)

The contract's `budget.budget_note` frames costing as "one run record per
(arm, prime) pair", but `deliverables`/`required_artifacts` name a single
`<RUN-ID>` path template for every artifact. This driver treats the entire
frozen grid as **one** run (`RUN-CANL-7cc073`) rather than ~14+ separate run
directories. This keeps the dual-auxiliary-tuple and cost-sharing
requirements auditable inside one `decision-rule-evaluation.json` rather than
needing cross-file consistency checks. Documented in
`harness/run_canl.py`'s own module docstring. Budget-wise this is far under
every ceiling (14.6s wall-clock, one run of `maximum_runs: 30`).

## D2 — CTRL uses 6 EXHIBITED-rank-1 curves, not a claimed true-rank curve set

`IDEA-20260807-761a8c` mentions a rank-2 example (p=101, Reg~1). This driver
uses exhibited rank 1 throughout: for each of 6 curves, one verified
non-torsion rational point was found by direct integer search
(`harness/canonical_height.py:find_small_point`), and covering-fraction
measurements use the closed-form cyclic subgroup `{[m]P0 : |m|<=3}`
generated by that point — never a claim that the point generates the curve's
full Mordell-Weil group. Constructing a *verified* rank-2 generator pair
without access to a curve database (LMFDB/Sage) was out of this session's
reach; using an unverified pair would risk silently wrong regulator/rank
claims, which is worse. "Exhibited rank" is this program's own established
convention (used identically elsewhere in this contract's own text, e.g.
"matched non-CM of the same exhibited rank").

## D3 — CTRL's 3 "CM" curves are drawn from 2 discriminants, not 3

`arms_frozen.CTRL_calibration` asks for 3 CM curves with `h(D_E)=1`. This
driver uses D0=-3 (two curves, `y^2=x^3+17`, `y^2=x^3+41`) and D0=-4 (one
curve, `y^2=x^3+9x`) — the only two class-number-one discriminants with an
explicit low-degree Weierstrass model this session can construct and verify
directly. The other 11 class-number-one discriminants (-7, -8, -11, -12,
-16, -19, -27, -28, -43, -67, -163) require Hilbert-class-polynomial curve
models this session does not build (a real risk of silently wrong curve
data recalled from memory rather than computed, which was avoided
deliberately).

## D4 — `canonical_height.py` computes the ARCHIMEDEAN LOCAL canonical
height only, not the full global height

Documented at length in the module's own docstring. Summary: the true
global canonical height needs Tate's reduction-type-dependent local height
corrections at every prime dividing the curve's discriminant, which this
session does not implement. The archimedean-only local height (X-only
projective doubling, mpmath, no gcd reduction) is individually exactly
quadratic under `End(E)` by the same telescoping-limit construction that
proves the global height's quadraticity — sufficient and exact for every
RATIO-based metric this contract actually reads (P2, the known-answer
checks, CTRL's shift diagnostic). No metric in this contract's frozen
predictions needs an absolute global height value.

## D5 — P2 (`ratio_of_minima`) is computed from the EXACT algebraic formula,
not re-measured transcendentally per swept `|D_E|`

Given G0 validates Lemma 2 (`hhat(alpha*P) = N(alpha)*hhat(P)`) on
known-answer cases (multiplication-by-m, the zeta_3 and i unit
automorphisms — all pass to float-precision-exact agreement), `P2` for each
C1 curve is computed as `sqrt(N(alpha_min(D_E)))` directly from the exact
integer norm formula (`harness/exp_canl.py:norm_form`/`alpha_min`), not by
constructing an actual CM endomorphism acting on a global curve at that
`D_E` (which is generically impossible for `h(D_E) > 1` — the overwhelming
majority of the C1 sweep — without constructing the ring class field, out of
reach here). This is mathematically exact given Lemma 2, not an
approximation; the "measurement" that could fail is Lemma 2 itself, and that
is what G0 tests.

## D6 — the dual-auxiliary-tuple rule, read literally, does not give
collision-free agreement at the tested (C0, r_Z) scale

`auxiliary_k_rule_frozen` fixes `k_i = i+1` (tuple A) / `k_i = slots+i`
(tuple B) for the first `s-1` slots and states "the two counts must agree
EXACTLY". Implemented literally (target slot's own multiplier taken as 1,
since the rule's text does not assign it a value), the two tuples'
reachable-count sums **do disagree on some cells** — worked out by hand and
confirmed by direct enumeration: for weights `(1,2)` vs `(1,3)` and a box
`[-1,1]`, the number of distinct achievable integer sums is 7 vs 9
respectively (not equal), because small, closely-spaced integer weights
collide differently depending on their exact values; only weights separated
by more than `2*C0*(sum of smaller weights)` are provably collision-free
for a symmetric box, and `k_i=i+1` does not satisfy that separation at
these `C0` values. This is a genuine finding about the frozen rule's own
text, not an implementation bug: `harness/run_canl.py:aux_tuple`'s docstring
records the exact reasoning. Per the contract's own
`invalidation_rules` ("The dual-auxiliary-tuple consistency check disagrees
on any cell -> that cell is INVALID... reported explicitly"), and per
`C1_INSTRUMENT_INVALID`/`C2_INSTRUMENT_INVALID`'s own `fires_when` clauses
("the dual-auxiliary-tuple consistency check disagrees for any
C1/C2 cell"), this disagreement is handled exactly as the frozen decision
rule specifies: both waterfalls terminate at `*_INSTRUMENT_INVALID`. This is
reported as the genuine, valid, non-fabricated result of applying the
frozen rule as written — not softened, not silently resolved by inventing a
different (unwritten) tuple construction.

## D7 — a real bug caught and fixed during construction (not a deviation,
recorded per AGENTS.md rule 9's spirit of never discarding an infrastructure
finding)

The first version of `c2_tautology_check` computed `zeta*P` as SCALAR
multiplication `E.mul(mu, P)` (mu = the CM eigenvalue from
`cm_eigenvalues`), which produced a spurious tautology failure. The correct
operation is applying the GEOMETRIC AUTOMORPHISM `(x,y) -> (mu*x, y)`
directly to the point's coordinates — a different operation from scalar
multiplication. Fixed before any tautology result was reported; the wrong
version never appeared in a committed run.
