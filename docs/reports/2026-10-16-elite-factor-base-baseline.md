# Index-calculus baseline and factor-base search boundary

**Date:** 2026-10-16. **Status:** source-linked assessment and derived capacity model; no new scientific trial or speed claim. **Scope:** prime-field, Koblitz, and ordinary binary curves with subgroup order near 2^50–2^63; decomposition arity `m=2..8`. This report uses existing committed results and source. It does not treat extrapolation as measurement.

**Size correction, 2026-10-17:** The reviewed Koblitz comparator uses the field `GF(2^53)` but its target prime `r=21,044,858,204,113` has bit length **45** (`log₂ r≈44.26`). It is a complete *53-bit field* comparator outside the requested 2^50–2^63 **prime-subgroup-order** range. The [exact Koblitz order screen](2026-10-17-koblitz-size-screen.md) finds no prime `r≥2^50` on the two standard binary Koblitz curves at field degrees 50–63. All subsequent matrices must give both field degree and target subgroup order; the user’s size phrase may refer to either, so neither reading is silently substituted for the other.

**Ordinary-binary input update, 2026-10-17:** A [non-descended GF(2^61) curve with prime subgroup near `2^59`](2026-10-17-ordinary-binary-fixture.md) now has an explicit generator, independently checked in Sage. This removes its input-selection dependency; its complete IC baseline remains unmeasured.

**Candidate representation update, 2026-10-17:** Two target-blind affine-space inputs now exist for that ordinary-binary fixture. The [subgroup-filtered m=8 base](2026-10-17-binary-subspace-base.md) has 249 selected representatives and an equal-size random control, but its sparse linearized equation is only a prefilter. The [cofactor-projected raw base](2026-10-17-binary-projected-base.md) has 265 selected representatives, an equal-size random control, and an exact sparse raw-x predicate with four target torsion channels. Both input sets were independently replayed in Sage. Neither has measured relation yield, solver degree, useful rank, or complete target cost. They are candidate arms; the full-pipeline baseline remains unmeasured.

**Corrections to [PR #2309](https://github.com/aburan28/crypto-autoresearcher/pull/2309):** the first baseline table omitted the later reviewed N53 target-certificate and ARM-composition runs; the latest accepted finite Koblitz comparator in this checkout is [RUN-KIC-a15078](../../research/cold_arm_composition_ic_20260921/REPORT.md), not the earlier calibration run. Its decision makes no program-baseline or scientific-status transition. The original capacity table also used `B^h` and called eight bytes per tail a floor. The [tail builder](../../src/crypto_autoresearcher/index_calculus/tails.py) stores sign-symmetric, nondecreasing tuples, and its compact array path uses 32-bit coordinates only below `2^32`. The table below now uses the exact combinatorial tuple-count upper bound and an explicit hypothetical 16-byte layout for wider coordinates. These figures are capacity preflight estimates, not measured allocation or lower bounds.

## Arity and memory preflight

For the current prime-field meet-in-the-middle engine, the source states `h=ceil(m/2)`, default factor-base size approximately `B=((m!N)/2)^(1/m)/2`, and total S3-equivalent count model `N^max(h,m-h+1)/m` ([README](../../src/crypto_autoresearcher/index_calculus/README.md), §§3, 5). Its [tail source](../../src/crypto_autoresearcher/index_calculus/tails.py) stores only nondecreasing factor-base indices and one sign orientation per negation pair. At most `U=2^(h-1) * binomial(B+h-1,h)` such tuples exist before zero-sum suffixes are discarded. The entries below use the code's integral `B=ceil(((m!N)/2)^(1/m)/2)` at nominal `N=2^b`, then multiply `U` by 16 bytes for a *hypothetical* 64-bit x-coordinate plus 64-bit packed-code array. This is a **derived upper bound for that proposed array payload**, not measured memory or a lower bound on any implementation. Sorting, construction, temporary arrays, the relation matrix, and the process add memory. The existing >32-bit path uses a Python map instead of this proposed array.

`*` At `m=2`, the engine does not construct the same multi-point tail table; `16B` is a comparison-sized hypothetical payload, not a claimed allocation. `U` is an upper bound on tuple count, so exceeding a memory envelope in this table does not prove the actual table cannot fit. The model puts `m=7` below `m=8` asymptotically in this generic split, so `m=8` needs an observed constant-factor or structural benefit before it can outrank `m=7`. The current numpy path itself stops at `p<2^32` ([README](../../src/crypto_autoresearcher/index_calculus/README.md), §4), independently of the table-capacity issue. At 32 bits, `m=7` still spent 1.3 times the S3-equivalent count of `m=5`; a proposed 45–54-bit crossover is explicitly an extrapolation in the source.

The arity index must be explicit in new algebraic trials: `m` factor-base points summing to a target give a direct summation polynomial `S_(m+1)`. Thus direct `S_8` represents seven summands plus the target; eight summands require `S_9`. A chain of `S_3` constraints can represent either without materializing the direct eliminant. The proposed high-arity comparison must report both the direct-polynomial construction attempt and the chained formulation, including failure or resource stop, rather than calling an `S_8` trial an `m=8` decomposition.

## Factor-base findings and next discriminating work

1. **Prime-field sparse algebra versus complete cost.** The existing [msolve comparison](../../src/crypto_autoresearcher/index_calculus/README.md), §2, found that a sparse multiplicative-subgroup membership equation improved its `m=2` per-target scaling on one 16-bit field, while `m=3` lost that benefit. At matched cardinality, the 12–32-bit complete-solve sweep found similar relation supply for small-x, random, and subgroup bases (§1). These are separate measured scopes. The next candidate should pair each base *and its equation formulation*, then measure construction, actual input support, observed solving degree, solver work, verified distinct rows, useful rank, final linear algebra, and blind target work. The [factor-base lab](../../research/factor_base_lab.md) defines matched random, affine-placement, fresh-seed, held-out-curve, and blinded-target controls. Sparse input alone is an admission signal, not an end-to-end score.
2. **Koblitz precomputed orbit bases and the actual query path.** The current composed N53 run's median internal setup is 0.761544 s and query kernel 1.844756 s, nested inside 1.856930 s of collection ([reviewed report](../../research/cold_arm_composition_ic_20260921/REPORT.md)); component medians are descriptive, not additive. Search Frobenius-stable nonlinear predicates and orbit representatives in a frozen, target-blind setup, then test the same unseen points with the composed implementation and rank/row checker. Charge base generation, orbit canonicalization, misses, duplicate rows, and target decomposition. Measure cold-start and genuinely amortized `T`-target costs separately; do not grant free preprocessing. The query path remains the largest named component, while further setup or matrix work needs a measured complete-cost rationale.
3. **Ordinary binary baseline before candidate promotion.** Use the now certified [GF(2^61) prime-subgroup fixture](2026-10-17-ordinary-binary-fixture.md), implement an arity-2 baseline collector and matched rho in the same field representation, and test the [249-point affine-subspace candidate against its equal-size random control](2026-10-17-binary-subspace-base.md) in a complete m=8 pipeline. Preserve the existing GF(2^51) map/evaluator gap as its own transport question. Further compare trace/norm, Hamming-shell, and sparse linearized predicate bases at equal *realized* point/orbit count and target set. Report degree of regularity separately from first-fall degree; [the internal literature inventory](../../research/lattice_index_calculus_20261015/coordinator/generator-handoff.yaml) records why first-fall degree alone is unsafe for binary descended systems.
4. **High-arity gate (`m=6,7,8`; direct `S_8` and chained `S_3`).** First measure symbolic construction time, coefficient/monomial count, degree, solver memory and planted correctness on bounded public synthetic inputs. Then run unplanted targets and full relation/rank/target phases only where a frozen memory envelope admits them. A timeout is censored. Streaming or external-memory 4+4 joins may make an `m=8` engine implementable, but sorting/I/O and repeated target lookups must be charged. A table that cannot be built is a concrete implementation/capacity obstruction, not an algebraic conclusion.

The existing [Coordinator decision](../../ledger/decisions/DEC-20260921-6648da.md) ranks a frozen own-process sample profile of the composed N53 IC and strengthened rho first, then a conditional Bloom-filter test, then factor-base density recalibration. This user's elite-base objective adds target-blind base/query co-design, but the next official dispatch and any reranking remain Coordinator acts. Ordinary-binary baseline construction and a prime solver-aware base/formulation test are independent preparation tracks. Any proposed elite base must be chosen using training targets disjoint from the held-out evaluation targets. Each candidate receives a frozen digest and cost ledger before the evaluator sees targets. Selection may optimize a Pareto front over wall time, CPU, memory and independently useful rows; a reported improvement in the user's criterion requires the same full end-to-end `S` boundary and a machine-readable progress-fidelity record.

## Acceptance and current obstruction

For each family/size/arity cell, an accepted new baseline or candidate needs a fixed curve and prime subgroup, public known-answer unseen target(s), exact base membership and digest, decomposition certificates, all attempts including misses/timeouts, verified marginal rank, solve/reconstruction, independent replay, exclusive phase times and memory, and matched rho on identical points. The complete cold and amortized formulas are `S_cold = C_base + C_rel + C_LA + C_target + C_verify` and `S_T = C_base + C_rel + C_LA + T(C_target + C_verify)` with measured reuse and one-time terms; record unsuccessful search and restart costs as well. A candidate wins a baseline cell only when the predeclared comparison finds a reproducible complete-cost gain within its resource envelope. Every row also reports the remaining distance to matched rho.

The specific [recorded obstruction](../../problems/full-width-ic-arity-grid-unmeasured.md) today is that there is no measured, executable 50–63-bit full-grid baseline across prime, ordinary binary, and `m=8`. The prime engine's 32-bit vectorized limit blocks direct reuse of its compact path, while the wide-array estimates flag potentially large memory demands that require measurement. A runnable continuation needs a bounded exact high-width engine or a memory-bounded alternative, plus an independently checked complete ordinary-binary pipeline. The next discriminating protocol should freeze one 50–53-bit public fixture per family, the current baseline, `m=2..8` capacity checks, and two candidate bases per family with equal realized size, target-blind selection, a matched-rho arm, and explicit `completed | censored | invalid | unavailable` outcome handling. Positive stage signals advance to complete solves; failures identify the exact representation, solver, or resource gate and do not close the mathematical direction.
