The checker independently matches all three reported trace-kernel dimensions
and checks six orbit-divisibility values. Its output calls six entries
`tuple_sum_reverifications`, but [source review of the checker](../../../experiments/EXP-FROB-91ee9c/runs/TASK-20260914-7119f2/checker.py)

also confirms those three `N` values prime by exact trial division. The
checker skips the other three entries for size. It does **not** recompute
tuple sumsets, `p_m`, or any C2/C3/C4 control arm, despite comments in its
source suggesting a broader re-enumeration. The three core cells are recorded
as completed; the extension cell is recorded
as `not_run_resource` after its 540-second checkpoint.

The [frozen specification's C8 control](../../../experiments/EXP-FROB-91ee9c/specification.yaml)
requires independent rechecking of every accepted tuple sum, slot membership,
subgroup order, Frobenius order, and rational identity. This checker covers
only a subset, so **C8 has not passed the specified gate** on this evidence.
The experiment's success criterion is therefore unestablished; this is an
instrument-validation gap, not a falsification of the mathematical hypothesis.
The [specific obstruction](../../../problems/frob-c8-independent-recheck-incomplete.md)
records the exit conditions.

The [raw-curve inventory](audit.json) records two eligible curves per core
cell, with subgroup orders `1051/10061`, `30841/3701`, and
`206461/117991` in cell order. Object-arm records retain aggregate partition
counts and ratios, not per-residue lists. C2 and C3 records exist only for
curve index 0 in each cell, as the original run report discloses. A full
independent C8 recheck must reconstruct the underlying subgroup and slot
membership rather than merely compare stored aggregate fields.

The audit independently recomputes the stored arithmetic on all **23**
`status: ok` partition records: eight object, three C2, six C3, and six C4.
For each it checks `p_m`, `U_neg`, tuple-count products, and the exact reduced
cost ratios for extras 0, 8, and 32. All match. An in-memory changed-ratio
control is rejected. These are aggregate identities; they do not validate
the counts from points, tuple sums, or slot membership.

## Provenance finding and boundary

The manifest records `code.head_commit=cb06b8c20c2d6559041c45c4a4b29dd7f132fdf5`
and says the run directory was untracked at execution start. The referenced
[`implementation.py`](../../../experiments/EXP-FROB-91ee9c/runs/TASK-20260914-7119f2/implementation.py)
is **absent** from that commit; `git cat-file` confirms the commit exists and
the driver path does not. The current run schema's `code.commit`,
`code.command`, and `environment` fields are also absent from the frozen
manifest. The separate command and environment files preserve useful evidence,
but they do not turn the pre-run HEAD into a commit containing the executed
driver. The extension-cell command file also distinguishes its illustrative
shell line from the command it says was used in practice.

The replay validates those stored checks and hashes. It does not rerun the
Sage generator, independently recompute the tuple sumsets or control arms,
establish original execution-source custody, or certify a performance or
discrete-log claim. Later FROB reviews and run directories are separate
evidence and are not adjudicated by this audit. No frozen run bytes or
historical result were changed.
