# MCP client configuration

The same server, over stdio, from all three clients. One server means one
retrieval contract: a claim an agent makes in Claude Code and a claim it makes
in Codex are backed by the same passages, with the same identifiers, and can
be checked against each other.

## Claude Code needs no copying

`.mcp.json` at the repository root **is** this server, committed. Every
worktree gets it, and `--directory kb` is relative so it resolves in each one
without editing. Nothing here has to be installed first: `uv run` builds
`kb/.venv` with the `index` and `mcp` extras on the first launch.

`kb/clients/claude-code.json` is the user-scoped form (`~/.claude.json`), for
connecting from outside the repository. That one cannot use a relative
`--directory`, so it carries an absolute path to fill in — as does
`codex.toml`, since `~/.codex/config.toml` is user-scoped too.

`.codex/config.toml` in this repository is generated by
`tools/generate_runtime_agents.py` — add the `mcp_servers` block to your user
config, not to the generated one. OpenCode reads a project-level
`opencode.json` from the repository root, so its snippet keeps the relative
path.

## Environment

All three pass the same environment. `CRYPTO_KB_CLIENT` and `CRYPTO_KB_AGENT`
are recorded in the query log, which is what makes "which agent asked what"
answerable later.

Only `CRYPTO_KB_CLIENT` is set in the client configs. Everything
machine-specific belongs in **`kb/.env`** (gitignored; copy `.env.example`),
because a value set in a client config overrides `.env` and would then have to
be edited in three places on every machine.

| variable | local default | notes |
| --- | --- | --- |
| `CRYPTO_KB_STORE_BACKEND` | `local` | `s3` in production |
| `CRYPTO_KB_LOCAL_ROOT` | `./.kb-corpus` | relative to `kb/`, which is the server's cwd |
| `CRYPTO_KB_QDRANT_URL` | `:memory:` | **set this**: `http://localhost:6333` |
| `CRYPTO_KB_COLLECTION` | `crypto_knowledge_v1` | bump on any vector-semantics change |
| `CRYPTO_KB_QUERY_LOG_PATH` | unset | e.g. `./.kb-queries.jsonl` |

An in-memory Qdrant is per-process, so an MCP server started with the default
`:memory:` has an empty index — it will answer every question with nothing and
give no reason. Point it at a running Qdrant (`make qdrant-up`) before
connecting a client; the server logs `qdrant_url_is_in_memory` at warning
level on startup when you have not.

A file-backed embedded index (`CRYPTO_KB_QDRANT_URL=./.kb-index`) needs no
Docker but is **single-writer**: a connected MCP server holds the lock, and
`crypto-kb ingest` will fail until the client disconnects. For a corpus that
is ingested while agents are running, use the server.

## Verifying all three see the same thing

```bash
crypto-kb search "KN-OPEN-001" --json | jq -r '.results[0].source_id'
```

then ask each client to call `search_knowledge` with the same query. All three
should return `open-problem:KN-OPEN-001` first, with the same `chunk_id` and
`content_hash`.
