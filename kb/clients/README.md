# MCP client configuration

The same server, over stdio, from all three clients. One server means one
retrieval contract: a claim an agent makes in Claude Code and a claim it makes
in Codex are backed by the same passages, with the same identifiers, and can
be checked against each other.

These are snippets to copy, not files that are read from here. In particular
`.codex/config.toml` in this repository is generated by
`tools/generate_runtime_agents.py` — add the `mcp_servers` block to your user
config (`~/.codex/config.toml`), not to the generated one.

## Environment

All three pass the same environment. `CRYPTO_KB_CLIENT` and `CRYPTO_KB_AGENT`
are recorded in the query log, which is what makes "which agent asked what"
answerable later.

| variable | local default | notes |
| --- | --- | --- |
| `CRYPTO_KB_STORE_BACKEND` | `local` | `s3` in production |
| `CRYPTO_KB_LOCAL_ROOT` | `./.kb-corpus` | filesystem corpus root |
| `CRYPTO_KB_QDRANT_URL` | `:memory:` | set to `http://localhost:6333` |
| `CRYPTO_KB_COLLECTION` | `crypto_knowledge_v1` | bump on any vector-semantics change |
| `CRYPTO_KB_QUERY_LOG_PATH` | unset | e.g. `~/.crypto-kb/queries.jsonl` |

An in-memory Qdrant is per-process, so an MCP server started with the default
`:memory:` has an empty index. Point it at a running Qdrant (`make qdrant-up`)
before connecting a client.

## Verifying all three see the same thing

```bash
crypto-kb search "KN-OPEN-001" --json | jq -r '.results[0].source_id'
```

then ask each client to call `search_knowledge` with the same query. All three
should return `open-problem:KN-OPEN-001` first, with the same `chunk_id` and
`content_hash`.
