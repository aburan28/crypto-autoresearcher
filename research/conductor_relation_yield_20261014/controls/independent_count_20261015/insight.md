# Independent ordered-count control

- **Question:** Can a separate oracle establish that the collector did not omit an unreported triple, including for a target with zero reported hits?
- **Workload and controls:** The same fully enumerable 19-point, six-base-point control as the collector test, all 18 nonidentity targets. `count_verify.cpp` uses extended-Euclidean field inversion and an unordered-map histogram of ordered pair counts; `collector.rs` uses Fermat inversion and a sorted table of explicit unordered index pairs. The Python test independently enumerates every ordered triple and replays the resulting collector rows.
- **Evidence:** The exact compile and control commands, hashes, environment, exit codes, elapsed times and raw RSS field are in [receipt.json](receipt.json). The compiler [stdout](0.stdout) and [stderr](0.stderr), and control [stdout](1.stdout) and [stderr](1.stderr), are retained. Both commands exited 0.
- **Completeness argument:** The Python verifier checks every reported canonical triple for uniqueness and the group equation, then sums its ordered multiplicity. The separate histogram computes the total ordered triple count for each target without using the collector's triple list. Equal counts imply that no valid unordered triple is missing, because every canonical triple has positive ordered weight. This argument applies to zero-hit targets as well.
- **Limits:** The argument depends on correct group arithmetic in the independent count oracle; the small exhaustive control and Python group-law replay test that implementation. The P29/P37 full-size count runs and resource receipts have not occurred, so full-size completeness is not yet established.
