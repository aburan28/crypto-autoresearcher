## Why this entry exists

`GOAL-MLKEM-004`'s goal record warns that its instrument "lives in an ephemeral
container at `/tmp/sagevenv` and WILL NOT survive session end", and requires every
batch to rebuild it from `KN-TECH-14efa5` and record the rebuild. On the first such
rebuild in a *new* container, the recorded recipe **did not complete**. It failed four
more times, in four new places, none of them covered by the entry.

This is not a defect in `KN-TECH-14efa5`. Everything it records is true of the
container it was written on. The defect is in reading a route that worked once as *the*
route.

**This entry is infrastructure, not a research finding.** It establishes no fact about
ML-KEM, no cost, and no security claim. It records how to obtain instruments.

## What actually happened, in order

`KN-TECH-14efa5` names two g6k fixes: build isolation hides Cython, and the missing
`libgmp.so` dev symlink. In this container **neither was the binding constraint**, and
four other things were.

| # | step | failure | fix |
|---|---|---|---|
| 1 | `python3 -m venv /tmp/sagevenv` | `ensurepip is not available` — `python3.12-venv` not installed, so the venv is created with no pip at all | `pip3 install --user --break-system-packages virtualenv` then `python3 -m virtualenv -p python3.12 /tmp/sagevenv`, which vendors its own pip (pip 26.2). Installing `python3.12-venv` also works where root is available |
| 2 | `pip install --no-build-isolation g6k` | `missing: line 81: aclocal-1.16: command not found` → `make: *** [Makefile:379: aclocal.m4] Error 127`. **No autotools of any kind** on the box: no `aclocal`, `automake`, `autoconf`, `m4`, `libtool` | `apt-get install automake autoconf libtool m4` |
| 3 | g6k compile | `g6k/siever.cpp:89:10: fatal error: Python.h: No such file or directory` — `python3.12-dev` absent | `apt-get install python3.12-dev` |
| 4 | `import g6k` | `ModuleNotFoundError: No module named 'pkg_resources'` — `g6k/siever_params.pyx` imports it, and setuptools 83 (pulled in by passagemath) no longer ships it | `pip install "setuptools<81"` (installs 80.10.2; g6k then imports with a deprecation warning) |

`passagemath-standard` 10.8.7 and `fpylll` 0.6.4 installed **exactly as the recipe
records**, first try, once step 1 produced a venv with pip.

### The route that does not work, and why the obvious trick fails

Before finding sudo, the natural autotools-free workaround for failure 2 is to touch
the shipped generated files in dependency order so `make` treats them as current.
**It cannot work here:** the g6k 0.1.2 sdist ships `configure`, `configure.ac`,
`Makefile.am` and `Makefile.in` but **ships no `aclocal.m4`**, so there is no file to
touch and `make` must genuinely generate it. Recorded because it is a cheap idea that
looks right and costs a build cycle to disprove.

### libgmp: the recorded fix was unnecessary here

The recipe's symlink fix (`ln -sf libgmp.so.10 $SCRATCH/gmplink/libgmp.so`, exported via
`LIBRARY_PATH`/`LDFLAGS`) exists because that container had no root. This container has
**passwordless sudo**, so `apt-get install libgmp-dev` provides
`/usr/lib/x86_64-linux-gnu/libgmp.so` properly. The symlink was applied anyway and is
harmless, but it was not what made the link succeed.

**These numbers are not identical to `KN-TECH-14efa5`'s and are not expected to be.**

benchmarks; both are single runs at toy dimensions recorded to show the code executes.

## What this does not buy

- **No ML-KEM result of any kind.** No break, no security proof, no FIPS 203 parameter
  set affected or cleared, no cost claim.
- **Not upstream Sage.** passagemath 10.8.7 is a redistribution, exactly as
  `KN-TECH-14efa5` states. Agreement under it is implementation agreement.
- **Not a portable recipe either.** This entry is as container-specific as the one it
  extends. Its content is the *class* of failure, below.

## The transferable lesson

`KN-TECH-14efa5`'s own closing lesson is that a failed install route is informative
about **one route** and nothing else. The symmetric error is the one this entry
records: a *successful* route is also informative about one container and nothing else.
That entry's two fixes were presented as "the two link-level fixes" when they were the
two fixes *that container's preinstalled package set happened to leave*.

Concrete discipline for the next rebuild, which would have saved most of this:

1. **Check for root first.** `sudo -n true`. If it succeeds, install the build
   dependencies rather than working around their absence — every workaround below is
   unnecessary and each costs a build cycle to discover.
2. **Enumerate build dependencies before building**, not on failure: a C++/Cython
   extension over autotools needs `automake autoconf libtool m4`, `python3.X-dev`,
   `python3.X-venv`, and the `-dev` package of every `-l` flag it links.
3. **Pin `setuptools<81`** in any venv that must import a package written before
   `pkg_resources` was removed. This will keep biting and is not g6k-specific.
4. Record the interpreter version with the recipe. This container's 3.12.3 versus the
   original's 3.11.15 is why failure 1 and failure 3 exist at all.
